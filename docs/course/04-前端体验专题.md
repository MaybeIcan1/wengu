## 0️⃣ 本章全景：一次"搜索"的完整旅程（新旧对照）

**改造前**（现状——每一跳的问题）：

```
用户敲字 → input事件 → 每键触发 load() → 请求海啸（敲"HashMap"6字=6次全量查询）
        → scroll 分页无记忆 → 返回列表回到第1页（丢失状态）
        → 数据没到就白屏 → 没数据就白板（分不清加载中/空）
```

**改造后**（本章织成的链路）：

```
用户敲字 ──1s 内停顿──> 防抖触发 ──> 状态写入URL ──> 骨架屏占位 ──> 数据/空态渲染
                                     （可分享/刷新可回 복）
      全链路每层都可观察：F12 Network 数请求数、Console 无红色无 warn
```

本章四层顺着这条链自底向上下（前端无数据库，映射为：**样式层 → 组件层 → 交互层 → 数据流层**）；每层标题下都标着"本层结束时系统能干什么"。

## 2️⃣ 组件层（结束时：三张业务页统一拥有"骨架/空/错"三态）

**业务需求**：三个页面各自手写 el-skeleton/el-empty 已出现两份重复代码——**重复即债**。
**缺乏什么（结构动作三件）**：新建 `frontend/src/components/StateBox.vue`（建在哪清楚了吧），把三态收拢成一个组件：

```vue
<script setup lang="ts">
// 统一状态盒：loading骨架 / 空态 / 挂了。三个业务页全部接入。
defineProps<{
  loading?: boolean
  empty?: boolean
  emptyText?: string
  rows?: number
}>()
</script>

<template>
  <el-skeleton v-if="loading" :rows="rows ?? 5" animated />
  <el-empty v-else-if="empty" :description="emptyText ?? '暂无内容'" />
  <slot v-else />
</template>
```

**三个业务页接入**（编辑文件的 diff 型说明——以 QuestionListView 为例，其他两页同构）：

```vue
<!-- 旧代码（两行删掉） -->
<div v-if="loading" class="grid"><el-skeleton .../></div>
<el-empty v-else-if="!rows.length" description="..." />

<!-- 新代码（换成 StateBox 包住内容区） -->
<StateBox :loading="loading" :empty="!rows.length" empty-text="还没有题目——去把你最近的八股记进来吧" :rows="8">
  <div class="grid"> ...卡片... </div>
</StateBox>
```

并记得 import：`import StateBox from '../components/StateBox.vue'`（Navbar 级别的基础组件不放到 api/ 自动）。

> ★ 抽问：为什么这套叫"状态模式"组件而不是 if-else 塞页面里？（答：状态间互斥关系收敛在一个 props 组合里 = 单一事实源；页面只关心"我处于哪个状态"，不关心骨架长啥样）

## 3️⃣ 交互层（结束时：搜索不再海啸，输入体验稳如老狗）

**业务需求**：搜"HashMap"不再发 7 次请求。
**技术抉择（决策点，都是面试题）**：
- **防抖（debounce）**：连续输入只认"最后一个稳定值" → _keyword for searching_（搜发达）
- 节流（throttle）：固定节奏拿最新值 → 适合滚动/持续事件，不适合搜索
- 选 300ms：人类连续打字间隔通常 <200ms，300ms 足够跳出"连续输入"判定又不会迟钝

```vue
<script setup lang="ts">
// QuestionListView 换上防抖（组件 underworld import @vueuse/core）
import { useDebounceFn } from '@vueuse/core'

// 搜索统一入口：Enter 立即搜（抢牌优先级），输入停顿 300ms 自动搜
const debouncedSearch = useDebounceFn(() => { pageNum.value = 1; load() }, 300)

watch(keyword, debouncedSearch)     // ★ 输入变化 → 自动出发（不再依赖手点查询按钮）
</script>
<!-- template：查询按钮保留（Enter也能触发），输入框 @keyup.enter 改调 search()（立即搜，跳过防抖） -->
```

**防抖成效验收方法（F12 实测，待会儿你会亲手跑）**：Network 面板清空 → 敲入"HashMap 6字" → 改造前 6~7 条请求；改造后 **1 条**（停顿后只发一次）。这是"体验优化"最直观的数字铁证。

## 4️⃣ 数据流层（结束时：搜索词/页码写进 URL，刷新/分享都恢复现场）

**业务需求**：朋友问"你那道 Redis 的题怎么查出来的？"——直接甩链接给他，打开就在同一个筛选现场。
**设计**：查询条件 ↔ URL query **双向绑定**：

```
用户改筛选 → router.replace({ query: {...} })   （replace=不污染历史记录栈）
页面刷新/分享链接 → 用 route.query 初始化条件 → load()
```

```vue
<script setup lang="ts">
// QuestionListView 数据流新增（替换原 keyword/tagIds/qType/pageNum 各自独立 ref 的"无状态"版本）

import { useRoute, useRouter } from 'vue-router'
const route = useRoute(); const router = useRouter()

// 条件从 URL 初始化（每次进页面都是"现场还原"）
const keyword = ref((route.query.k as string) ?? '')

// 条件变化 → 同步 URL（replace：前端改查询历史不留垃圾）
function applyQuery() {
  router.replace({
    query: {
      ...route.query,
      k: keyword.value || undefined,
      page: pageNum.value > 1 ? String(pageNum.value) : undefined,
    },
  })
  load()
}
// load() 里改用 route.query 做数据源（category 已是先例）——分页翻页也走 applyQuery
</script>
```

> ★ 抽问：为什么用 `router.replace` 不用 `push`？（答：筛选是同一状态的变形——push 会把栈塞满搜索历史，浏览器回退键变成回去验证上一条筛选，迷宫体验；replace=**静默更新现场**）
> 💣 债登记：`keyword` 防抖后 applyQuery 每次防抖触发都会 replace——第 7 章缓存会把"每次筛选"都变成便宜操作，URL 同步策略届时复评（URL chore 与缓存的配合）。
